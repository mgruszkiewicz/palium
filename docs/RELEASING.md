# Releasing Palium

Updates ship over-the-air via [Sparkle](https://sparkle-project.org). The app reads
an appcast from GitHub Pages; the actual binaries are GitHub Release assets.

```
git tag v1.1.0 → .github/workflows/release.yml
                   ├─ build + test
                   ├─ Palium-1.1.0.zip   (Sparkle enclosure, EdDSA-signed)
                   ├─ Palium-1.1.0.dmg   (first-time download)
                   ├─ GitHub Release      ← assets live here
                   └─ gh-pages branch     ← appcast.xml + notes/1.1.0.html
                        └─ https://mgruszkiewicz.github.io/palium/appcast.xml
```

## Cutting a release

```sh
git tag v1.1.0
git push origin v1.1.0
```

That is the whole process. The tag drives the version:

| Field | Value | Why |
|---|---|---|
| `CFBundleShortVersionString` | tag without `v` (`1.1.0`) | shown to users |
| `CFBundleVersion` | `git rev-list --count HEAD` | Sparkle's ordering key — must only ever increase |

Because the build number is the commit count, **always tag a commit that is ahead of
the previous release's commit.** Tagging an older commit produces a lower build number
and Sparkle will not offer it as an update.

The workflow asserts that the built app's `Info.plist` matches the tag before signing,
so a mismatch fails the run rather than shipping a bad appcast.

## One-time setup

### 1. Export the EdDSA private key into a GitHub secret

The key generated by `generate_keys` lives in your login Keychain and has to be
exported for CI:

```sh
curl -sSL -o sparkle.tar.xz \
  https://github.com/sparkle-project/Sparkle/releases/download/2.9.4/Sparkle-2.9.4.tar.xz
mkdir sparkle && tar -xJf sparkle.tar.xz -C sparkle
./sparkle/bin/generate_keys -x sparkle_private_key.txt
```

Add the file's contents as the repository secret **`SPARKLE_PRIVATE_KEY`**
(Settings → Secrets and variables → Actions → New repository secret), then delete
the local copy:

```sh
rm sparkle_private_key.txt
```

Keep a backup somewhere safe (a password manager). **Losing this key means existing
installs can never be updated again** — they only trust `SUPublicEDKey`, and you
cannot change that key in an app that is already on someone's disk. Confirm the
public half still matches what is in `palium/Info.plist`:

```sh
./sparkle/bin/generate_keys -p
```

### 2. Enable GitHub Pages

Settings → Pages → Source: **Deploy from a branch**, branch `gh-pages`, folder `/`.

The branch does not exist yet; the first release creates it. Run the release once,
then set the Pages source.

### 3. Check Actions permissions

Settings → Actions → General → Workflow permissions must be **Read and write**, so
the workflow can create releases and push to `gh-pages`.

## How the app consumes it

`palium/Info.plist` carries the whole client-side configuration:

- `SUFeedURL` — where to look for the appcast
- `SUPublicEDKey` — the only thing that makes an update trusted
- `SUEnableAutomaticChecks` / `SUScheduledCheckInterval` — background check, daily

`UpdaterService` owns the `SPUStandardUpdaterController`, exposed through
*Palium ▸ Check for Updates…* and the Settings ▸ Updates tab.

## Verifying an appcast by hand

```sh
make release-artifacts
./sparkle/bin/sign_update Palium.zip          # signs using the Keychain key
python3 scripts/appcast.py /tmp/appcast.xml \
  --version 42 --short-version 1.1.0 \
  --url https://example.com/Palium-1.1.0.zip \
  --length "$(stat -f%z Palium.zip)" --signature "<sig from sign_update>"
```

To test the update flow end to end, run a build with a *lower* version than the
published one and use *Check for Updates…*:

```sh
VERSION=0.0.1 BUILD=1 make build-unsigned
open build/DerivedData/Build/Products/Release/palium.app
```

## Code signing

Palium currently ships ad-hoc signed and un-notarized. Sparkle is fine with this —
the EdDSA signature alone is sufficient to trust an update — but first-time users
must right-click ▸ Open to get past Gatekeeper.

To move to Developer ID later, add to the release workflow before the DMG step:

1. Import the `.p12` into a temporary keychain.
2. Build with `CODE_SIGN_IDENTITY="Developer ID Application: ..."` and
   `--options runtime` instead of `CODE_SIGN_IDENTITY=-`.
3. `xcrun notarytool submit --wait` on the DMG, then `xcrun stapler staple`.

Nothing about the appcast or the EdDSA key changes. Sparkle keeps accepting updates
across the transition because the EdDSA signature stays valid on its own.
